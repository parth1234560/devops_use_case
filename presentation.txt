AWS High Availability Web Application Project
============================================

Project Owner Context
---------------------
Parth initially owned networking, security, IAM, and CI/CD. Palak was supposed to own compute, load balancing, database, DNS, monitoring, and testing, but Parth now needs to complete the full project.

Project Goal
------------
Build a highly available AWS application infrastructure using Terraform. The infrastructure should run an application across multiple Availability Zones, expose it through an Application Load Balancer, keep application servers private, use a managed Multi-AZ database, automate deployments with CI/CD, and prove reliability through failure testing.

High-Level Architecture
-----------------------
User -> Route 53 domain -> Application Load Balancer in public subnets -> EC2 instances in private subnets managed by Auto Scaling Group -> RDS database in private subnets.

Supporting services:
- S3 remote backend for Terraform state.
- Terraform lock support to avoid concurrent state corruption.
- IAM roles and instance profiles for EC2, CodeBuild, CodeDeploy, and CodePipeline.
- CodePipeline for source, build, and deploy stages.
- CodeBuild for building/testing application code.
- CodeDeploy for blue-green deployment to the Auto Scaling Group through the ALB.
- CloudWatch for logs, metrics, alarms, scaling signals, and deployment rollback alarms.

Interview Explanation
---------------------

Short project intro:
"This project provisions a highly available AWS web application infrastructure using Terraform. It uses a custom VPC across two Availability Zones, public subnets for the Application Load Balancer and NAT Gateway, private subnets for EC2 and RDS, security groups with least-privilege traffic flow, Auto Scaling for EC2, Multi-AZ RDS for database availability, and a CI/CD pipeline using CodePipeline, CodeBuild, and CodeDeploy blue-green deployments."

Why VPC:
A VPC gives isolated networking control. We define CIDR, subnets, route tables, gateways, and security boundaries instead of using default networking.

Why public and private subnets:
Public subnets host internet-facing resources like ALB and NAT Gateway. Private subnets host EC2 and RDS so they are not directly exposed to the internet.

Why two Availability Zones:
Two AZs improve availability. If one AZ has an issue, ALB and ASG can continue serving traffic from the other AZ.

Why NAT Gateway:
Private EC2 instances need outbound internet access for updates, package installation, and agents, but they should not accept inbound internet traffic. NAT Gateway provides outbound-only access.

Why Internet Gateway:
The Internet Gateway allows public subnet resources like ALB to communicate with the internet.

Security group design:
- ALB SG accepts 80/443 from the internet.
- EC2 SG accepts app traffic only from ALB SG.
- RDS SG accepts DB traffic only from EC2 SG.
This creates layered security and prevents direct public access to EC2 and RDS.

Why ALB:
Application Load Balancer distributes HTTP/HTTPS traffic, performs health checks, and routes users only to healthy targets.

Why Auto Scaling Group:
ASG maintains desired EC2 capacity, replaces unhealthy instances, and can scale based on metrics like CPU.

Why Launch Template:
Launch Template defines repeatable EC2 configuration such as AMI, instance type, security group, IAM instance profile, and user data.

Why RDS Multi-AZ:
RDS Multi-AZ creates a standby database in another AZ. AWS manages synchronous replication and automatic failover, improving database availability.

Why Terraform remote backend:
Remote state in S3 keeps Terraform state centralized. Locking prevents two people from applying changes at the same time and corrupting state.

Why not commit tfstate or tfvars:
tfstate can contain sensitive data and real resource IDs. tfvars can contain secrets or environment-specific values. They should stay local or secure.

Why CI/CD:
CI/CD automates build, test, and deployment. It reduces manual deployment mistakes and gives repeatable releases.

Why blue-green deployment:
Blue-green keeps the current working environment while deploying a new version separately. Traffic shifts only after health checks pass. If the new version fails, traffic rolls back.

Why CloudWatch:
CloudWatch provides metrics, logs, alarms, and operational visibility. It can trigger scaling and rollback decisions.

Common Interview Questions and Answers
--------------------------------------

Q: What is high availability?
A: High availability means the application remains accessible even when part of the infrastructure fails. In this project, HA is achieved with multiple AZs, ALB, ASG, and RDS Multi-AZ.

Q: What is the difference between public and private subnet?
A: A public subnet has a route to an Internet Gateway. A private subnet does not expose resources directly to the internet and usually routes outbound traffic through NAT.

Q: Why are EC2 instances in private subnets?
A: To reduce attack surface. Users access the app through ALB, not directly through EC2 public IPs.

Q: What is the traffic flow?
A: User traffic goes to Route 53, then ALB in public subnets, then EC2 instances in private subnets, then the app connects to RDS in private subnets.

Q: What is the role of route tables?
A: Route tables decide where network traffic goes. Public route table sends internet-bound traffic to IGW, private route table sends internet-bound traffic to NAT Gateway.

Q: What does ALB health check do?
A: It checks whether instances are healthy on a configured path and port. Unhealthy instances stop receiving traffic.

Q: What happens if one EC2 instance fails?
A: ALB marks it unhealthy and stops sending traffic to it. ASG launches a replacement instance to maintain desired capacity.

Q: What happens if one AZ fails?
A: Because resources span two AZs, ALB can route traffic to healthy instances in the remaining AZ.

Q: What is Terraform state?
A: Terraform state maps Terraform configuration to real cloud resources. It is required for planning changes and detecting drift.

Q: Why use modules?
A: Modules separate responsibilities, improve reuse, and make the code easier to maintain. This repo uses modules for networking and IAM and should add compute, database, and CI/CD modules.

Q: What is IAM least privilege?
A: Giving each role only the permissions it needs. For example, EC2 should get only CloudWatch/SSM/app-specific permissions, not administrator access.

Q: What is CodeBuild?
A: CodeBuild runs build and test commands defined in buildspec.yml.

Q: What is CodeDeploy?
A: CodeDeploy automates deployment to EC2 or ASG and can manage blue-green deployment with ALB traffic shifting.

Q: What is CodePipeline?
A: CodePipeline orchestrates stages such as source, build, and deploy.

Q: What is rollback?
A: Rollback restores the previous healthy version when the new deployment fails health checks or triggers alarms.

Q: What are important security choices in this project?
A: Private EC2/RDS, security group chaining, encrypted RDS storage, no committed secrets, IAM least privilege, and remote state encryption.

Q: What would you improve for production?
A: Add HTTPS with ACM, WAF, multi-NAT for stronger AZ independence, stricter IAM, centralized logging, backup policies, cost alerts, secret rotation, and separate environments for dev/stage/prod.
